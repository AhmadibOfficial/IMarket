# IMK-002 local authentication and tenancy

This implementation is for synthetic local fixtures. Real authentication and seller access remain disabled by RELEASE_GATES.md pending human identity/security review. Production startup refusal, demo mode requirement and loopback binding remain in place. No payments or external identity providers are enabled.

Run `npm run db:migrate` to apply both idempotent migrations. Existing sample products have no merchant owner and cannot be used to create merchant campaigns. An operator must explicitly assign synthetic inventory to a synthetic merchant locally; the API does not accept ownership assignment from clients.

To provision local fixtures, run `APP_DEMO_MODE=true npm run account:create -w @imarket/api` and supply one JSON object on stdin, then EOF. Fields are `alias` (starts with `demo_`), `password` (14 characters minimum, 256 bytes maximum), `role` (`buyer` or `merchant`) and, for merchants, `merchantAlias` (also starts with `demo_`). Use a password manager or protected stdin; never put passwords in command arguments, shell history or tracked files. No default account password, public registration, or admin provisioning route exists. Passwords use salted scrypt (N=32768, r=8, p=1); database stores only the versioned hash.

`POST /api/auth/login` accepts only `alias` and `password`. It returns a random 256-bit bearer token once, with `Cache-Control: no-store`. Send it in `Authorization: Bearer ...` for writes. Tokens have an absolute 15-minute lifetime, no refresh, and are stored only as SHA-256 digests in PostgreSQL. Logout deletes the current session. Every request reloads current role, merchant and disabled status; disabled accounts and administrators are rejected. Clients should keep tokens in memory, not URLs or localStorage. Local HTTP is restricted to loopback; any future remote access requires TLS and release review.

The global guard allows public GET catalog/groups/health and login, then denies all handlers except explicitly authorized operations. Merchants create campaigns only for products selected with their server-derived merchant ID. A composite database FK also enforces matching product/campaign ownership. Buyers join public campaigns and create simulated orders; account ownership comes from the session. Merchants cannot join or checkout as buyers. Admins have no bypass. Public catalog and campaign reads are intentionally shared and contain no account/session data. New merchant-private reads must be explicitly tenant-scoped before adding them to the guard.

## Administrator MFA design (not activated)

Administrator password-only login always returns the same generic failure as invalid credentials. No admin API capability is currently enabled. Before enabling: human-reviewed enrollment of two WebAuthn authenticators, user verification required, server-generated one-time challenges bound to session/origin/RP ID and expiring in five minutes, atomic challenge consumption, credential revocation, and single-use hashed recovery codes with a reviewed recovery procedure. Require recent MFA for privileged operations, deny unenrolled admins, audit enrollment/recovery/role changes without credentials, and test replay, origin mismatch, revoked authenticators and concurrent challenge reuse. TOTP fallback would require encrypted seeds, drift/replay checks and a separate reviewed design. None of these mechanisms is claimed implemented.

## Abuse limits and operational gaps

Atomic PostgreSQL upserts enforce fixed 15-minute windows across API processes: 30 login attempts per socket IP, 5 per alias, and 120 authenticated mutations per account. Failed and successful logins both count. Limits run before password hashing, return 429 when exceeded, and fail closed on storage errors. IPs and aliases are hashed before storage; hashes are pseudonymous and need retention controls. Forwarded headers are not trusted. Shared IP denial of service and alias lockout remain known tradeoffs; review adaptive throttling before external access. The local service uses bearer headers rather than ambient cookies, so cookie-based CSRF does not apply.

Before enabling real access: implement/admin-test MFA, review abuse/tenancy, add audit events and operational monitoring, schedule expiry cleanup of sessions and stale auth_limits, bound concurrent scrypt work at an approved ingress, define retention/password reset/recovery, and review transport and client token handling. This milestone does not claim production readiness or a completed security audit.

## Verification

`npm run check:offline` includes dependency-free password tests. `npm run test -w @imarket/api` compiles the API and tests actual service, controller and global guard classes using a database double, including wrong roles, cross-tenant creation, malformed inputs, revocation, expiry, disabled users and parallel login limits. `IMARKET_TEST_DATABASE_URL=... npm run test -w @imarket/api` additionally exercises migrations, SQL tenant constraints and parallel rate limits on a disposable local PostgreSQL database. The test refuses non-loopback hosts, database names outside `imarket_test_*`, URL query overrides and production mode. Use a freshly created dedicated database, never an existing application database. It creates a random schema, excludes `public` from its search path, and drops that schema afterward; migrations may install pgcrypto in the dedicated database. Never point the test URL at customer or production data.

In environments where the default Node test runner reports only file-level results, expose individual cases and skips with `node --test --experimental-test-isolation=none packages/commerce-domain/*.test.cjs apps/api/test/*.test.cjs` after building the API. This supplemental command was verified with Node 24.19.0; it does not turn an unset PostgreSQL URL into a successful integration run.
