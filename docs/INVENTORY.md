# IMK-003 local inventory and order lifecycle

Only synthetic inventory is represented. `stock_demo` is available stock, not evidence of supplier verification. No payment, fulfilment, financing or identity integration is enabled.

Apply migrations 001–003 with the local migration runner. Migration 003 is repeatable and preserves existing orders as `legacy` and existing memberships as unreserved; it does not retrospectively debit inventory. Legacy orders cannot be cancelled through the reservation API. Use fresh synthetic fixtures to test the lifecycle.

`POST /api/demo-checkout` requires `productId`, integer `quantity` (1–10) and `idempotencyKey` (8–80 ASCII letters, digits, underscores or hyphens). Buyers must reuse the key for retries of the same logical request. The key is scoped to the authenticated account. A transaction advisory lock serializes same-key requests; a unique index backs the key. Replays return the same order including its current lifecycle. Different payloads under the same key return 409. An atomic conditional stock update and order insertion commit together; insufficient stock and unsafe totals roll back. No key is accepted from a different account as ownership evidence.

New orders start `reserved`. `POST /api/demo-orders/:id/cancel` with `{}` requires the owning buyer and changes `reserved` to `cancelled`, returning stock exactly once. Repeated cancellation is safe. Replaying creation after cancellation returns the cancelled order without another reservation.

Each new group join reserves one item within the campaign transaction. Campaign row locks serialize joins, capacity checks and terminal transitions; all campaign operations lock campaign before product. Duplicate accounts or aliases roll back any stock change. Both group joins and checkout contend on the same stock row.

The owning merchant can use `POST /api/groups/:id/cancel` or `/expire`, with `{}`. Before the deadline, cancellation closes the campaign and releases reserved items. At/after the database deadline, expiration wins: membership below the minimum becomes `expired` and releases stock; qualifying membership becomes terminal `confirmed` and retains stock. These terminal transitions are irreversible; a confirmed group cannot be cancelled. Repeated expiry/cancellation never releases twice. Joins after the deadline persist expiry before returning 409. Public group reads derive deadline state but do not mutate inventory. Idle groups require the merchant expiry endpoint; there is no background scheduler. Confirmed reservations remain held for a future explicitly approved fulfilment lifecycle.

The global guard permits group transitions only to merchants and order cancellation only to buyers, retaining authentication and mutation quotas. SQL selects enforce merchant/account ownership. All responses remain simulated with no financial capture.

PostgreSQL tests use the existing dedicated loopback `imarket_test_*` target guard and random schema cleanup. They cover migration reruns, concurrent first-request retries, key conflicts/account scoping, final-stock checkout and join contention, overselling, capacity, duplicate membership rollback, ownership, repeated cancellations and expirations, late joins, confirmed reservations and nonnegative stock. CI configuration supplies a disposable PostgreSQL service; no CI run or external service has been started from this workspace.

## IMK-003 shopping journey

Apply migration 004 after 001–003. Existing catalog rows remain published; new merchant products begin as drafts. Only published products with positive available synthetic stock appear in public browsing. Reservation SQL also checks publication, so stale clients cannot buy an unpublished item. Merchant draft creation validates bounded text, integer kobo prices and stock. Publishing/unpublishing uses the authenticated merchant tenant; ownership fields supplied by clients are rejected.

The Next.js shop and `/merchant` workspace log in through `/api/auth/login`, keep bearer tokens only in component memory, and use the existing 15-minute sessions, hashed credentials, role checks and mutation quotas. Provision synthetic accounts with the existing `account:create` tool; no public registration or real identity collection is added. Reloading loses the session and cart. Logout revokes the session when reachable and clears local state. Never enter real credentials or customer information.

`POST /api/cart-checkout` accepts `{items:[{productId,quantity}],idempotencyKey}` with 1–20 unique products, quantity 1–10 per item. It rejects client prices/totals and ownership fields. The whole cart reserves stock and creates one order per item in a single transaction, ordered by product ID to avoid cross-cart product lock inversion. Any item failure rolls back all orders and reservations. A buyer-scoped batch lock and primary key prevent concurrent/retried batches from creating duplicates; canonical cart payload conflicts return 409. The checkout response contains order IDs, with actual totals available from the owned order list. Retry the same key after an ambiguous transport/server failure. The web/mobile cart stays locked for such retries; definitive validation/stock conflicts unlock it. Keys and carts are in-memory only; after reload, review owned orders before making another checkout.

`GET /api/orders` returns at most 100 recent orders for the authenticated buyer or merchant tenant, including their persisted total, quantity and lifecycle. `POST /api/merchant/orders/:id/fulfill` accepts `{lifecycle}` and advances only `reserved → processing → shipped → delivered`. Repeating the current transition is safe; skipping/backtracking fails. The owning merchant alone can act. These are simulated labels only; no shipping integration or actual delivery is claimed. Cancellation and fulfillment lock the same order row. Buyers may cancel only `reserved` orders (or replay an already cancelled order); processing/shipped/delivered/legacy orders cannot release stock. Reservation totals remain unchanged during fulfillment.

Flutter has a practical buyer interface for login, cart, retryable simulated checkout, owned status and eligible cancellation. Merchant work remains in the web app. Flutter SDK analysis must run where its cache is writable; Android API routing also requires a permitted host loopback forwarding setup. No background expiry worker, order pagination, durable client cart, product editing/restocking or real fulfillment integration is included.

Validation: `npm run validate:milestone` runs offline source/policy checks and domain tests, backend compilation, all domain/API tests including guarded PostgreSQL tests with zero failures/skips/cancellations/todos, then Next.js production compilation. Logs and JSON results are retained under a printed `/tmp/imarket-validation-*` path. The required database target must be a dedicated loopback `imarket_test_*` database. GitHub Actions supplies an isolated PostgreSQL service and executes this same gate. `npm run repair:milestone` explicitly invokes a local Codex correction runner only after non-infrastructure failures, at most twice, rerunning the full gate after each correction. Infrastructure failures stop immediately. Existing tests, release rules and validation scripts are hashed and protected from automatic edits; any detected alteration stops for manual review. The workflow makes no commits, pushes, merges or deployments. Generated source corrections still require human diff review.
